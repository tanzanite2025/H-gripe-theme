# 支付渠道内部成本核算与利润快照架构

更新时间：2026-09-23

## 状态与决策

状态：长期架构决策，**暂不实施代码、数据库迁移或后台页面**。

本项目采用以下明确决策：

> 支付渠道的收单、退款、拒付、提现/结算和换汇费用均为商家内部经营成本。它们用于成本核算、对账和未来单笔利润分析，绝不加入客户应付金额，也不改变客户支付、订单价格、订金或退款金额。

消费者只支付已在商品、运费、税费、优惠和订金规则中确认的订单金额。支付渠道成本不作为客户收费项目，不在店铺或客户售后界面显示，也不提供客户发起直接退款的入口。

## 1. 问题与目标

PayPal、信用卡收单（例如 Stripe）、支付宝和微信支付的商户合同通常包含比例费、固定费或两者组合；退款、拒付、提现/结算和换汇也可能产生独立成本。若仅把一个无币种的 `fee_value` 放在支付方式记录上：

- 无法表达 `3.49% + 0.49 USD` 等组合费率；
- 无法区分 JPY、USD、CNY 等固定费用和对应的币种精度；
- 无法区别收单、退款、拒付、提现和换汇成本；
- 后台改动费率后，无法可靠解释历史订单的利润；
- 容易误把商户经营成本耦合到客户价格或售后退款。

本架构的目标是建立一条独立、可审计的内部成本账：

1. 后台可以按渠道、支付产品、币种和适用范围维护商户成本规则；
2. 每笔支付和退款都冻结其发生时的预估成本快照；
3. 渠道回执和结算账单可补充实际成本并与预估成本对账；
4. 后续单笔利润、渠道成本和经营报表只读取冻结事实，不使用当前规则反推历史；
5. 现有客户支付、订单计价和受控售后退款流程保持不变。

## 2. 不变量与非目标

### 2.1 必须保持的不变量

```text
商品/运费/税/优惠/订金规则
              │
              v
        客户订单应付金额 ──────────> 支付渠道请求与金额校验
              │                              │
              │                              └─ 现有支付确认、Webhook 和幂等链路
              v
    既有受控售后流程决定客户可退款金额

支付渠道内部成本规则 ──> 支付/退款成本快照 ──> 对账与未来利润分析
                         （只读旁路，不回写客户金额）
```

- 客户应付金额不得因为支付渠道成本而增加或减少。
- `expected_total_minor`、订单支付快照、渠道请求金额和回调金额校验继续只使用客户已确认的订单应付金额。
- 商品定制订金的不可退比例及其他售后政策继续由商品/订单/售后域决定；渠道成本不得改变其可退金额。
- 客户不直接发起退款。现有“订单后 24 小时内提交售后申请”的受控入口仍是唯一客户侧售后路径。
- 后台售后审核和退款执行继续根据售后原因、商品合同、订单定价快照和退款策略决定客户退款；成本规则只记录商家损益。
- 支付域内部成本规则不得向店铺 API、客户页面或不具备财务权限的后台角色泄露。

### 2.2 非目标

本决策不实现以下能力：

- 向消费者收取 payment surcharge、结账附加费或退款手续费；
- 以支付方式改变商品价、运费、税费、优惠、订金或客户退款额；
- 自动批准、拒绝或扣减任何售后退款；
- 用后台配置的预测值代替渠道回执、结算账单或财务事实；
- 以当前费率重算历史订单的已冻结成本。

## 3. 领域归属

渠道成本归属**支付域**，但与消费者可见的支付方式和网关凭据分层管理。

```text
支付域
├─ 渠道账户（Provider Account）
│  └─ 凭据、回调、沙箱/生产、商户主体、可用性
├─ 收款方式（Payment Method）
│  └─ 客户可见名称、启用状态、排序、渠道绑定
├─ 渠道成本规则（Provider Cost Rule）
│  └─ 商户合同的预估成本；仅内部使用
├─ 支付与退款成本快照（Cost Snapshot）
│  └─ 某笔事实发生时适用的规则和计算结果
└─ 对账与成本差异（Reconciliation）
   └─ 预估成本与渠道实际账单/回执的比较

订单/售后域
├─ 决定客户实付与可退款金额
└─ 仅读取已冻结的成本事实，供审核、经营分析或报表展示
```

其他域不得直接查询渠道成本规则表。它们只能消费支付域提供的只读快照或受限查询服务。这样可防止商品、营销、运费或售后逻辑误将内部成本带入客户价格。

## 4. 后台信息架构

成本配置应放在支付后台的渠道子域，而不是通用系统设置或客户可见支付方式表单中。目标导航如下：

```text
支付
├─ 收款方式
│  └─ 前台按钮、启用状态、排序、渠道绑定
├─ Stripe
│  ├─ 接入配置
│  ├─ 支付产品与可用性
│  ├─ 渠道成本规则
│  └─ 对账与成本差异
├─ PayPal
│  ├─ 接入配置
│  ├─ 支付产品与可用性
│  ├─ 渠道成本规则
│  └─ 对账与成本差异
├─ 支付宝
│  ├─ 接入配置
│  ├─ 支付产品与可用性
│  └─ 渠道成本规则
├─ 微信支付
│  ├─ 接入配置
│  ├─ 支付产品与可用性
│  └─ 渠道成本规则
├─ 支付记录与退款
└─ 支付风控
```

“渠道成本规则”是商户合同、报价或历史账单的受控录入面，不保存或显示网关密钥。修改权限应独立于普通支付方式启用权限；规则创建、变更、停用和删除都必须记录审计信息。

## 5. 渠道成本规则模型

### 5.1 一条规则表达的内容

长期目标模型为 `ProviderCostRule`。一条规则对应某商户主体与渠道的某种成本，而非一个笼统的“手续费”：

| 类别 | 说明 | 示例 |
| --- | --- | --- |
| 归属 | 渠道账户、可选收款方式/支付产品 | `paypal-main`、`paypal checkout` |
| 操作类型 | `charge`、`refund`、`dispute`、`payout`、`fx_conversion` | 收单与提现必须分开 |
| 适用范围 | 交易币种、结算币种、市场/国家、卡地区、支付产品等 | Stripe 国际卡、USD、US 市场 |
| 组合成本 | 比例费率、固定费用、最低/最高费用 | `3.49% + 49 USD cents` |
| 生命周期 | 生效/失效时间、优先级、启用状态、规则版本 | 合同续约后新版本优先 |
| 追溯来源 | 合同编号/报价版本、录入依据、备注 | 不保存敏感合同附件内容到审计摘要 |

固定费用必须使用 `fixed_cost_minor` 和明确的 `fixed_cost_currency`。比例费必须使用精确的 `rate_decimal`，不得使用二进制浮点。

### 5.2 成本类型必须分开

以下成本不允许共用一个 `fee_value`：

| 操作类型 | 含义 | 与客户金额的关系 |
| --- | --- | --- |
| `charge` | 正常收单成本 | 只计入商家内部订单成本 |
| `refund` | 渠道针对退款收取或不退还的成本 | 不改变客户获批退款金额 |
| `dispute` | 拒付/争议处理费及资金损失 | 只计入商家风险与经营成本 |
| `payout` | 从渠道余额提现或结算到银行的成本 | 属于结算成本，不是订单收单费 |
| `fx_conversion` | 渠道收单或结算时的换汇成本 | 独立记录，不能伪装为收单比例费 |

### 5.3 规则匹配

支付域在成本快照创建时按以下优先级选择一条有效规则：

1. 操作类型、渠道账户和支付产品必须精确匹配；
2. 币种和市场/国家等限定条件越具体，优先级越高；
3. 生效时间必须覆盖事实发生时间；
4. 同等具体度使用明确配置的 `priority`；
5. 仍出现歧义时失败并产生可处理的内部成本配置告警，不能静默猜测。

规则缺失不能阻断客户的支付成功或后台退款执行；系统应记录“成本未知/待配置”状态，避免经营数据被伪造为零成本。是否将该告警提升为运营发布门禁，由后续运营策略决定。

## 6. 不可变成本快照

### 6.1 支付成功快照

一笔支付被验证成功并持久化后，支付域异步或同事务地创建一条内部 `PaymentCostSnapshot`。其最小内容为：

- 订单、支付尝试、交易、渠道账户、收款方式和支付产品标识；
- 订单客户应付金额与币种（仅作成本计算基数，不改写订单）；
- 匹配到的规则 ID、规则版本和匹配维度；
- 比例费、固定费、最低/最高限制和精确舍入规则；
- 计算出的预估 `charge` 成本及其币种；
- 快照状态：`estimated`、`actual_confirmed`、`unknown` 或 `reconciled`；
- 创建时间、计算器版本和审计关联。

规则后续被编辑、停用或删除都不得修改这条快照。

### 6.2 退款与其他事件快照

每次后台受控售后流程实际产生退款执行、拒付事件、提现/结算或换汇事实时，支付域按该事实创建独立快照：

- `RefundCostSnapshot` 绑定退款执行与渠道退款事实；
- `DisputeCostSnapshot` 绑定渠道争议/拒付事实；
- `PayoutCostSnapshot` 和 `FXCostSnapshot` 绑定结算事实。

退款快照记录客户已批准和实际发送给渠道的退款金额作为参考输入，同时单独记录商家预计/实际渠道成本。客户退款金额的决定过程仍由订单、售后和退款域拥有。

### 6.3 预估与实际

后台维护的合同规则只能产生**预估成本**。渠道回调、余额明细、结算报告或人工导入的对账结果产生**实际成本**。

```text
合同成本规则 ──> 预估成本快照
渠道回执/账单 ──> 实际成本事实
                         │
                         v
                  对账差异与原因
```

实际成本不得覆盖预估快照；应以追加事实或明确的关联字段保留两者和差异。这样可以解释跨境卡、汇兑、分层合同或渠道临时调整带来的偏差。

## 7. 与订单、售后和退款的协作边界

### 7.1 正常支付

1. 订单和支付域按现有规则确定客户应付金额。
2. 网关以该金额创建支付请求，现有回调继续核验金额、币种、签名与幂等。
3. 支付验证成功后，支付域记录内部成本快照。
4. 快照创建失败或规则缺失只进入内部告警/待核算队列，不回滚已验证的客户支付，不修改订单总额。

### 7.2 24 小时售后与退款

1. 客户仅可在规定窗口通过售后申请入口提交请求；店铺不提供直接退款动作。
2. 后台按商品定制订金约定、售后原因、订单定价快照及现有退款控制决定客户可退金额。
3. 已批准的退款由现有受控退款执行流程调用渠道。
4. 支付域为该退款记录预估和/或实际的 `refund` 成本快照。
5. 渠道是否退还原收单费、另收退款费或在后续账单扣费，只影响内部成本和利润分析，不影响已批准的客户退款金额。

### 7.3 特殊原因

商家取消、缺货、重复扣款、支付异常或履约失败等情形，仍由售后/退款策略决定客户退款；成本快照只用于衡量商家损失和渠道差异。定制订金按公开约定比例不退同样属于商品合同和售后政策，不得通过渠道费规则实现或绕过。

## 8. 未来单笔利润分析

单笔利润页面尚未实施。实现后应聚合不可变经营事实，而非读取当前后台配置：

```text
订单收入快照
  - 商品实收、运费、税费、优惠、订金处理结果
成本事实
  - 采购/生产/包装/入库运费（各自领域快照）
  - 支付收单、退款、拒付、提现与换汇成本快照
  - 售后和履约成本（可用时）
  = 单笔毛利 / 贡献利润 / 实际结算差异
```

利润页面必须清楚区分：

- 预计利润：基于已冻结的预估渠道成本；
- 已对账利润：已获得实际渠道成本和结算事实；
- 暂不可核算：缺少规则、渠道回执或上游成本事实。

不得用今天的 PayPal、Stripe、支付宝或微信费率重新计算过去订单。

## 9. 数据治理、权限与审计

- 渠道凭据继续使用现有加密配置边界；成本规则不得复制密钥、签名密钥、私钥或 API token。
- 成本规则读取、编辑、导出和对账导入应使用单独的财务/支付权限；普通运营仅可按最小必要范围读取结果。
- 规则变更审计至少保存规则 ID、版本、非敏感匹配范围、金额/费率字段变化摘要、有效期、操作者、时间、IP 和请求路径；不保存原始凭据、完整合同或敏感账单内容。
- 成本快照一经创建不可原地编辑；更正通过追加实际成本、冲销/调整事实或明确的对账记录完成。
- 导出利润与成本数据需要访问审计、权限控制及面向财务的脱敏策略。

## 10. 现有过渡状态

当前 `payment_methods` 的历史 `fee_value`、`min_amount` 和 `max_amount` 没有币种和完整业务语义，不能安全迁移为渠道合同成本。发布前迁移已选择将旧固定金额和门槛归零，避免制造两位小数的错误假设：

- 旧固定支付费用归零；
- 旧最低/最高支付金额门槛归零；
- 无币种的历史非零配置需在新模型上线后由运营按合同重新配置；
- 无币种的百分比费率可作为历史参考，但只有明确属于比例成本时才可在新规则中人工确认录入。

在新成本规则与快照能力实施前，`payment_methods` 仍只承担客户可见支付方式、可用性和现有兼容契约；不得继续将其单一费用字段扩展为渠道成本账本。

## 11. 分期实施计划

### Phase 0：本架构决策

- 本文档成为内部渠道成本边界的设计依据。
- 不改动客户价格、支付请求金额、订单/售后退款决定或网关回调链路。
- 在发布前清空无币种的历史固定金额配置，并由运营准备渠道合同资料。

### Phase 1：规则与后台维护

- 新增独立的成本规则数据模型、精确金额/费率校验、审计与权限。
- 在各渠道后台提供“渠道成本规则”页面。
- 实现规则预览/模拟，显示匹配原因与估算结果；该工具不写订单，也不面向客户。

### Phase 2：成本快照

- 在支付确认、退款执行、争议和结算事实旁新增不可变内部成本快照。
- 添加规则缺失、冲突和异常成本的运营告警。
- 不改变现有付款成功、退款成功与订单状态转换的事务边界。

### Phase 3：实际成本与对账

- 解析渠道可用的费用回执，或提供受控账单导入。
- 形成预估/实际成本差异列表、待处理原因和审计记录。

### Phase 4：单笔利润与经营报表

- 建立只读单笔利润页和按渠道/市场/币种聚合的成本报表。
- 明确显示预计值、实际值、差异和缺失数据；不得写回订单价格或售后决定。

## 12. 实施验收条件

任何实现本架构的改动至少应满足：

1. 配置渠道成本规则不会改变任何客户订单报价、`expected_total_minor`、渠道请求金额或店铺展示价格。
2. 任一支付成功后，存在可追溯的预估成本快照，或明确的 `unknown` 状态与告警。
3. 规则修改后，新事实使用新规则，历史快照保持原值和原规则版本。
4. 售后批准的客户退款金额与是否存在/如何配置 `refund` 成本规则无关。
5. 部分退款、多次退款、重复支付退款和渠道退款失败各自建立关联成本事实，不重复计费。
6. 实际渠道成本可以和预测成本并存并计算差异，不覆盖原始预测。
7. 客户 API、店铺页面和客户售后接口不暴露内部成本规则、内部成本快照或利润数据。
8. 新增测试覆盖币种精度、组合费率、规则匹配、规则版本冻结、退款关联、幂等和权限边界。
