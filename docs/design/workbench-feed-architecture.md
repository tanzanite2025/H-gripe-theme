# Workbench Feed Architecture

Status: implementation baseline
Owner: storefront content and catalog integration
Last updated: 2026-09-08

## 1. Positioning

Workbench Feed is a lightweight, high-frequency, workshop-first activity
timeline. It captures real assembly, repair, measurement, and fitment work in
short entries, then places the products mentioned in that work beside the
entry.

The feed is intentionally closer to a workshop log than a blog. A useful entry
can be two or three photographs and a few plain sentences. It should take
roughly thirty seconds to publish and should not require a rich text editor,
video editing, or an external social platform.

The business goals are:

- lower the effort required to publish trustworthy, regular content;
- show evidence that the store has a real workshop and real processes;
- let a reader inspect the mentioned product without leaving the timeline;
- protect Core Web Vitals by using first-party media and no embedded video
  scripts.

## 2. Product interaction decision

The product tag at the bottom of an entry is a product information affordance.
It is not a QuickBuy trigger.

When a reader clicks a tag, the storefront calls the existing global product
detail bottom sheet directly:

```ts
openGlobalProductDetailBottomSheet({
  id: taggedProduct.product_id,
  variantId: taggedProduct.variant_id,
  slug: taggedProduct.product_slug,
  title: taggedProduct.display_title,
})
```

The global product detail sheet remains the owner of product media, current
price, specifications, availability, add-to-cart, and buy-now actions. The
Workbench domain does not copy that purchase flow and does not dispatch
`quickbuy:open-entry`.

The stored title and price are snapshots for the feed label and for historical
context. The detail sheet reads the current product record by slug when opened.
If a product is later unavailable, the historical label remains readable but
the purchase actions are governed by the current product detail domain.

## 3. SEO and routing

There is one canonical public timeline route:

```text
/resources/workbench
```

The route is an aggregate page. It has no `/workbench/:id` detail pages and no
thin-content URLs for individual entries. The first page is SSR-rendered and
subsequent pages are loaded in batches of ten as the reader reaches the end.

The home page may render a small recent-workbench preview containing the latest
three entries. The preview links to `/resources/workbench`; it does not create a second
URL for each entry.

The timeline page owns its canonical URL, title, description, and language
signals. Feed entries are not added to the product sitemap and are not sent to
the blog route catalog.

Placing the route under `resources/` makes it discoverable in the Resources
footer section; the desktop Resources mega menu lists it through its explicit
navigation card. `/resources/workbench` is the only supported public route.

## 4. Data contract

### 4.1 FeedEntry

```text
FeedEntry
├── id: uint
├── entry_number: string       // server-generated, e.g. LOG-089
├── published_at: datetime
├── locale: string              // default en
├── content: text               // 1-300 Unicode characters
├── tags: string[]              // maximum 12 normalized labels
├── status: draft | published | archived
├── media: FeedMedia[]          // maximum 4 images
└── tagged_products: TaggedProduct[]
```

`entry_number` is generated by the service and is not trusted from the client.
It reduces the emotional cost of a long publishing gap while keeping the
timeline readable.

### 4.2 FeedMedia

```text
FeedMedia
├── id: uint
├── file_path: string
├── width: int
├── height: int
├── file_size_kb: int
├── caption: string
└── sort_order: int
```

Workbench media is uploaded through the existing `MediaService`. The upload
uses the `workbench-feed/` source prefix and receives the existing derivative
pipeline (thumbnail, card, and large WebP/JPEG/PNG outputs). The Workbench
table stores the selected display reference and intrinsic dimensions; it does
not implement a second image processor.

The first-party storage path is suitable for a local VPS volume and Cloudflare
edge caching. A future R2 switch remains a storage configuration change.

### 4.3 TaggedProduct

```text
TaggedProduct
├── product_id: uint            // logical reference, deliberately no FK
├── variant_id: uint?           // optional logical reference
├── product_slug: string        // current detail-sheet lookup key
├── display_title: string       // snapshot used on the tag
├── price_minor: int64           // snapshot in the currency's smallest unit
├── currency: string
├── direct_action: detail_drawer
└── available: bool              // latest catalog state at write time
```

The product picker is a read-only projection of the product catalog. It does
not preload the complete `Product` aggregate and does not write to catalog
tables. Product IDs and variant IDs are stored without database foreign keys so
that product deletion or archival cannot destroy historical workshop context.

## 5. Storage and performance

The expected first-stage storage is the existing local VPS upload volume:

```text
/uploads/workbench-feed/
```

The existing media service validates the source image, records dimensions,
stores the source, and emits derivatives. The desired operating target is a
maximum source width around 1200px for workshop images and an effective display
weight of roughly 40-80KB per image after WebP conversion. The existing media
limits remain the security boundary for the first implementation.

At 500 entries with two images each, the expected media volume is approximately
50-80MB. At 5,000 entries it is approximately 350MB, subject to the source
image distribution and retained derivatives.

Cloudflare R2 is the second-stage option. No Workbench table or handler should
assume local filesystem paths; storage references remain relative/object
references that the existing storage service can resolve.

## 6. API surface

Public:

```text
GET /api/v1/workbench-feed/entries?locale=en&page=1&page_size=10&tag=Gravel
```

The public endpoint returns only `published` entries, newest first.

Admin:

```text
GET    /api/admin/workbench-feed/entries
GET    /api/admin/workbench-feed/entries/:id
POST   /api/admin/workbench-feed/entries
PUT    /api/admin/workbench-feed/entries/:id
PATCH  /api/admin/workbench-feed/entries/:id/status
DELETE /api/admin/workbench-feed/entries/:id
POST   /api/admin/workbench-feed/media
GET    /api/admin/workbench-feed/product-options
```

The media endpoint is a multipart upload. The entry create/update endpoint
accepts the uploaded media references and logical product selections. The
service resolves each product selection from the read-only catalog projection
and writes the complete entry, media rows, and product snapshot rows in one
database transaction.

## 7. Back-office workflow

The admin page is a dedicated Workbench Feed screen, separate from blog
editing. It contains:

- a short textarea for the workshop note;
- locale and status controls;
- tag entry;
- drag-and-drop or file selection for up to four images;
- per-image caption editing and removal;
- read-only product search and selection;
- a single publish/save action.

Draft, published, and archived states are explicit. Publishing does not
require a Nuxt rebuild because the storefront reads the API at request time.

## 8. Permissions

Workbench has its own permission namespace:

```text
workbench_feed:view
workbench_feed:create
workbench_feed:edit
workbench_feed:delete
```

Admin and manager receive all four permissions. Editor receives view/create/edit
but not delete. Viewer receives view. Support does not receive Workbench
permissions by default.

## 9. Boundaries and failure handling

- Workbench never writes products, variants, price books, carts, orders, or
  QuickBuy configuration.
- A product tag is a snapshot plus a logical product reference, not an FK.
- The public timeline never exposes draft or archived entries.
- Entry content, tag count, media count, and media dimensions are validated on
  the server; client validation is only a usability aid.
- A failed child insert rolls back the entry transaction.
- A failed image derivative upload is reported by the existing MediaService;
  no partially accepted media reference is saved into a feed entry.
- A missing product at read time does not make the entire timeline fail. The
  tag can remain visible as historical context and its detail action can be
  disabled when no current slug is available.

## 10. Observability and future work

The first release needs normal request tracing and admin audit coverage from
the existing middleware. It does not need a social engagement counter, comment
system, or external syndication worker.

Later work may add R2 configuration, a media cleanup report, feed analytics,
and optional localization. None of those should change the single-route SEO
model or move product purchase ownership out of the global product detail
drawer.
